# WS 订阅入库方案记录（2026-03-07）

## 1. 背景

当前项目已具备两个 WebSocket 行情接口能力：

- `/ws/quote`：真实 TDX 五档行情推送
- `/ws/mock/quote`：模拟五档行情推送

现阶段目标不是继续扩展 WebSocket 协议本身，而是在现有项目基础上，承接 WS 相关行情逻辑，建设一条可持续运行、可配置、可入库、可归档的数据采集链路。

---

## 2. 用户目标

用户希望在当前项目中实现“订阅入库”能力，核心诉求如下：

1. 使用 `MySQL + 业务侧 batch save` 的方式进行实时行情落库。
2. 通过数据库中 `system_config` 配置表，按固定周期轮询获取：
   - 订阅标的
   - 订阅时间
   - 其他采集参数
3. 先将实时行情以“增量行新增”的方式写入当日增量表。
4. 在当日收盘后（例如 16:00），对当日增量数据进行压缩处理：
   - 提取必要字段
   - 进行聚合/归档
   - 写入历史表
   - 删除当日增量表数据

---

## 3. 用户期望

结合沟通内容，用户期望的并不是“跟随在线 WS 客户端连接行为落库”，而是：

- 将现有 WS 行情能力抽象为服务端独立的数据采集能力
- 由配置驱动订阅，而不是由浏览器/客户端在线状态驱动
- 采集过程可持续运行，适合生产使用
- 白天高频落增量，盘后低频做归档压缩
- 最终形成“实时增量表 + 历史归档表”的双层结构

这意味着该能力本质上应被定义为：

> 配置驱动的实时行情采集与存储系统，而不是简单的 WebSocket 消息旁路写库。

---

当前仓库已经具备以下可复用能力：

## 5. 对用户方案的分析结论

总体判断：**方案合理，可落地，且比直接在 `/ws/quote` 发送链路上写库更适合生产。**

### 5.1 合理点

#### 1）MySQL + batch save

这是正确方向。

- 高频行情不适合逐条同步写入
- 批量写可以降低数据库连接与事务开销
- 当前项目已有 MySQL + xorm 实践，迁移成本低

#### 2）配置表轮询驱动订阅

作为 MVP 是可接受的。

优点：

- 不依赖前端在线连接
- 配置集中管理
- 更符合生产环境“后台采集任务”的控制方式

边界：

- 配置变更生效会存在轮询延迟
- 订阅时间若要求秒级精度，1 分钟轮询会偏粗

#### 3）先落当日增量表

非常合理。

白天应优先保证：

- 采集不中断
- 落库链路简单稳定
- 不在实时路径做复杂聚合

因此当日表建议采用 append-only 的行式写入方式。

#### 4）盘后压缩归档

这是典型且合理的冷热分层方案。

优点：

- 将高频写和复杂聚合解耦
- 白天只做采集与写入
- 收盘后做压缩、清洗、聚合，利于查询和成本控制

## 6. 我的规划建议

### 6.1 总体原则

不要把入库逻辑直接挂在某个 WS 客户端连接上，而应实现为：

> 服务端独立的 Quote Recorder / Quote Collector。

它复用现有 WS 背后的行情抓取能力，但不依赖 WS 客户端是否在线。

### 6.2 推荐链路

建议拆成 4 层：

#### A. 配置层

周期性轮询 `system_config`，生成当前有效采集配置：

- 是否启用
- 行情源（real / mock）
- 订阅表达式
- 采集时间窗
- 采样频率
- 批量写大小

#### B. 采集层

将配置中的订阅表达式展开成代码集合后，按周期获取行情：

- 真实行情：复用 `fetchQuotesBatched`
- 模拟行情：复用 `mockPusher.generateQuote`

#### C. 写入层

采集线程只负责投递数据到内存队列。

单独的 writer 协程负责：

- 聚合批次
- 批量写入 MySQL 增量表
- 控制 flush 大小与 flush 周期

#### D. 归档层

盘后任务负责：

1. 读取当日增量表
2. 做必要字段压缩与聚合
3. 写入历史表
4. 校验成功后清理增量表

---

## 7. 推荐数据模型

### 7.1 当日增量表

建议建立类似 `quote_tick_realtime` 的表，按行追加。

建议字段至少包括：

- `id`
- `source`
- `code`
- `exchange`
- `event_ts`
- `trade_date`
- `last`
- `open`
- `high`
- `low`
- `close`
- `volume`
- `amount`
- `inside`
- `outside`
- `seq`
- `raw_json`
- `created_at`

如果需要保留五档盘口，则继续加：

- `bid1_price ~ bid5_price`
- `bid1_vol ~ bid5_vol`
- `ask1_price ~ ask5_price`
- `ask1_vol ~ ask5_vol`

### 7.2 历史归档表

建议建立 `quote_tick_history` 或更明确的聚合表，例如：

- `quote_1s_history`
- `quote_1m_history`
- `quote_daily_summary`

具体取决于业务最终希望保留：

- 秒级回放
- 分钟级聚合
- 仅保留必要统计指标

---

## 8. 需要重点补强的地方

### 8.1 幂等与去重

这是方案能否稳定运行的关键。

建议至少保证以下任一能力：

- 当日增量表存在业务唯一键
- 写入采用 UPSERT / IGNORE
- 应用侧先去重再 batch insert

建议唯一键候选：

- `source + code + event_ts`
- 若同一秒可能多次采样，则可加 `seq` 或采样批次号

### 8.2 时间语义

必须明确区分：

- `event_ts`：行情时间/采样时间
- `ingest_ts`：写库时间
- `trade_date`：交易日

否则盘后归档、跨日处理、补采重放都会混乱。

### 8.3 配置热更新方式

不建议每轮轮询后直接全量重启采集器。

更合理的方式：

- 计算配置 diff
- 增加新的订阅
- 停止失效的订阅
- 更新采样参数

### 8.4 盘后归档必须幂等

归档任务必须允许重复执行而不会重复插历史表。

建议保证：

- 历史表也有业务唯一键
- 或按批次归档并保留批次号
- 删除增量表之前先确认归档成功

### 8.5 删除策略

不建议第一版就直接物理删除。

更稳妥的方案是：

1. 先标记 `archived=1`
2. 确认历史表落库成功
3. 再做异步清理

---

## 9. 对“1 分钟轮询配置”的建议

该设计在 MVP 阶段可接受，但需要明确其业务语义：

- 配置变更最多延迟 1 分钟生效
- 若业务要求“秒级启停”，则后续需改造为：
  - DB 轮询 + version 控制
  - 或消息通知/事件驱动

推荐 `system_config` 中至少包含：

- `config_key`
- `config_value`
- `enabled`
- `updated_at`
- `version`

若配置较复杂，建议独立一张订阅配置表，而不是把所有字段挤在通用 key-value 中。

## 10. 推荐的最小可行落地顺序

### Phase 1：先打通最小闭环

实现：

- 从 `system_config` 读取配置
- 展开订阅代码
- 每秒抓取真实行情
- batch save 写入 MySQL 增量表

此阶段先不做：

- 复杂聚合
- 盘后自动删除
- 多策略并发采集

### Phase 2：补归档能力

实现：

- 16:00 后触发归档任务
- 从增量表压缩出历史表
- 验证后清理增量表

### Phase 3：补生产增强项

实现：

- 配置 diff 热更新
- 去重与重试机制
- 失败补偿
- 指标监控与采集日志

---

## 11. 最终建议

基于当前讨论，推荐采用以下判断：

1. 用户提出的总体方案是合理的。
2. 该方案应被定义为“服务端独立行情采集与存储链路”，而不是“在线 WS 消息顺手写库”。
3. 第一阶段优先做：
   - MySQL 增量表
   - 配置轮询
   - batch save
   - 任务化运行
4. 第二阶段再做：
   - 盘后压缩归档
   - 清理策略
   - 幂等与补偿

如果后续进入实施阶段，建议进一步输出以下设计产物：

- MySQL 表结构草案
- `system_config` / 订阅配置表字段设计
- 采集任务状态机设计
- 盘后归档规则说明
- 接口与任务运维说明
