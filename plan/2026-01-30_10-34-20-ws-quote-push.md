# Plan: WebSocket 实时推送五档盘口

🎯 任务概述

在现有 `web` REST API 基础上新增 WebSocket 服务端接口 `/ws/quote`，按 500ms 周期推送“盘口五档”行情数据给订阅客户端；支持单股/多股订阅；同时保持现有 REST API（尤其是交易数据接口）不变。

本计划优先落地“最小可行解（MVP）”：可连接、可订阅、可稳定推送、可控性能、可验证；复杂的字段级增量（仅变化字段）作为可选增强，避免过度设计。

📋 执行计划

1. 明确最小验收口径与兼容边界
   - 定义服务端仅新增 `/ws/quote`，不改动既有 REST API 行为与返回结构。
   - 消息协议以 JSON 为主：支持 `subscribe/unsubscribe/ping`；服务端返回 `pong/snapshot/delta/error`。

2. 依赖与模块准备
   - 在 `web/go.mod` 增加 `github.com/gorilla/websocket` 依赖。
   - 复用现有 `tdx` 替换配置（`web/go.mod` 已 `replace github.com/injoyai/tdx => ../`），避免引入重复 SDK。

3. 新增 WebSocket Hub（连接管理 + 订阅管理）
   - 新建 `web/ws_hub.go`：维护客户端集合与订阅映射（code -> clients）。
   - 定义线程安全的数据结构与事件循环（register/unregister + 广播/单播），确保不会因单个慢客户端阻塞全局推送。

4. 新增 WebSocket Handler 与消息处理
   - 新建 `web/ws_quote.go`：实现 `/ws/quote` 升级握手、readPump/writePump。
   - 解析客户端消息：
     - `subscribe`：仅支持明确股票代码列表（如 `000001`、`600000`）；不支持 `*`/`sh:*` 等全量订阅语法（按当前业务约束简化）。
     - `unsubscribe`：同样仅支持明确股票代码列表。
     - `ping`：立即回 `pong`。
   - 处理错误：非法 action / codes 格式返回 `{"type":"error",...}`。

5. 实现 QuotePusher（500ms 拉取 + 推送）
   - 在 `web/ws_quote.go` 中实现一个后台推送器：
     - 每 500ms 计算“当前所有客户端需要的 codes 并集”。
     - 分批拉取：按 80/批（可配置）拆分 codes（即便当前不订阅全量，也可避免偶发大订阅导致单次请求过大）。
     - 推送策略（MVP）：
       - 首次订阅或每 30s：发送 `snapshot`（对客户端订阅集合）。
       - 其余周期：发送 `delta`（仅对发生变化的 code，变化判定可用轻量 hash/序列化对比）。
       - 为了降低复杂度：`delta` 消息内可以携带“整条 quote 对象”，客户端按 code 覆盖即可；字段级 diff 作为后续增强。
   - 并发方案（可选）：优先保持实现简单；如后续出现拉取耗时问题，再引入 `tdx.Pool`（`pool.go`）做并行拉取。

6. 路由注册与服务启动集成
   - 修改 `web/server.go`：注册 `http.HandleFunc("/ws/quote", handleWSQuote)`。
   - 在 `main()` 启动时启动 Hub 与 QuotePusher 的 goroutine（可在第一次客户端连接时惰性启动，MVP 可直接启动）。

7. 功能验收（按 verify-env / AGENTS.md）
   - 容器内编译：
     - `docker exec -it go-dev-container bash -c "cd /app/tdx-api/web && go build -o tdx-api ."`
   - 容器内测试：
     - `docker exec -it go-dev-container bash -c "cd /app/tdx-api/web && go test ./..."`
   - 容器内启动：
     - `docker exec -it go-dev-container bash -c "cd /app/tdx-api/web && go run ."`
   - 健康检查（宿主机）：
     - `curl http://localhost:8080/api/health`

8. WebSocket 验收用例（可追踪、可复现）
   - 连接：`wscat -c ws://localhost:8080/ws/quote`
   - 心跳：发送 `{"action":"ping"}`，期望收到 `{"type":"pong",...}`。
   - 单股订阅：发送 `{"action":"subscribe","codes":["000001"]}`，期望 500ms 周期收到 `snapshot/delta`。
   - 多股订阅：发送 `{"action":"subscribe","codes":["000001","600000"]}`。
   - 退订：发送 `{"action":"unsubscribe","codes":["000001"]}`，期望该 code 不再推送。
   - 非法订阅：发送 `{"action":"subscribe","codes":["*"]}`，期望收到 `type=error`（明确提示不支持全量订阅）。

⚠️ 风险与注意事项

- 性能与带宽：尽管当前业务不会订阅全量，但仍需限制单连接订阅量与单次推送大小，避免误用导致服务压力异常。
- 稳定性：TDX 服务端连接不稳定时需要重连/降级；MVP 可先记录错误并继续下一轮。
- 并发安全：订阅集合与客户端集合需要严格的锁/事件循环，避免 data race。
- 兼容性：避免修改现有 REST 行为；新增路由不应影响静态文件与已有 `/api/*` 路由。
